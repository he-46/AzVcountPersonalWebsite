# 2026-09-26 评论与投稿修正记录

本文件逐项记录本次代码修正。改动只在本地工作区；未包含环境变量、密码或密钥，也未自动执行生产数据库变更。

## 修正 1：评论与举报改用 JSON 请求体

- 原因：此前 `text`、`nickname`、`reason` 被附在 POST URL 查询参数里，可能进入代理访问日志，长评论也容易触及 URL 长度上限。
- 改动：`POST /api/comment` 接收 `{contentId,text,nickname}`；`POST /api/report` 接收 `{contentId,reason}`；前端同步改为发送 JSON 请求体。
- 兼容性：旧的 query/form 调用方需同步升级。部署时前后端应一起发布，避免请求契约不一致。
- 验收：在浏览器 Network 中检查 Request URL 不含评论或举报正文，Request Payload 包含相应 JSON；提交后仍先审后发。

## 修正 2：输入字数与后端一致

- 评论前端最大 500 字，对齐后端限制；举报原因前端最大 255 字，对齐数据库列和后端限制。
- 后端仍独立校验长度，不能依赖浏览器的 `maxlength`。

## 修正 3：评论分页与查询索引

- `GET /api/content/{id}/comments` 改为分页响应，默认 20 条、单次最多 50 条；仍只返回已审核评论的公开 DTO，按创建时间和 ID 稳定升序。
- 文章页增加“加载更多评论”，失败可重试，不会重复追加相同 ID。
- 新库 `schema.sql` 加入 `idx_comment_feed (parent_id, type, status, created_at, id)`。**已有数据库必须在备份并检查索引不存在后，单独执行** `backend/sql/migrations/20260926_comment_index.sql`；`CREATE TABLE IF NOT EXISTS` 不会为旧表补索引。
- 兼容性：旧客户端若按数组读取评论接口，需要改读响应中的 `records`、`current`、`pages`。

## 修正 4：投稿图片失败清理与像素限制

- 图片在写盘前先检查实际字节数；对可由服务器解码的格式，先读取宽高并限制最长边 12000 像素、总像素 4000 万，再生成缩略图。
- 单次文件写入失败时清理已经写下的原图或缩略图；一批图片中后续文件失败、数据库写入失败或事务最终回滚时，补偿删除本次已保存的文件。
- WebP 在服务器没有解码器时仍允许作为原图保存，但不会生成缩略图，也无法做解码后的像素检查；仍受 10 MB 文件大小限制。需要严格像素限制时，应增加可审计的 WebP 解码支持或禁用 WebP。
- 文件系统与数据库没有真正的分布式事务；进程在提交与补偿之间直接崩溃仍可能留下孤儿文件。后续可加定期扫描、对账和清理任务。
